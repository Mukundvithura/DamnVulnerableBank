1.0 Executive Summary

1.1 Overview

A white-box penetration test was performed against BankVWA, a PHP/MySQL online-banking application, to identify and demonstrate common web application vulnerabilities. Every test was carried out against a local instance using application source code and seeded accounts. The assessment confirmed ten distinct, exploitable weaknesses spanning the OWASP Top 10, several of which lead directly to full account or server compromise.

1.2 High-Level Test Outcomes

  • Authentication can be bypassed entirely with a single SQL-injection string, granting administrator access without a password.
  • An administrator feature allows arbitrary operating-system commands to run on the server.
  • Directory traversal exposes server-side files, including database credentials.
  • Stored cross-site scripting lets one customer run script in another customer's browser.
  • A cross-site request and a clickjacking overlay can both move money / take over an account with one disguised click.

1.3 Overall Risk Rating

Considering the number of high-impact issues and the ease of exploitation, BankVWA's overall risk exposure is assessed as EXTREME. Multiple findings require no prior authentication and no specialised tooling.

1.4 Prioritized Recommendations

  1. Use parameterised queries everywhere and verify hashed passwords in code — never build SQL from user input.
  2. Escape all output with a context-aware encoder and add a Content-Security-Policy.
  3. Remove shell execution from the diagnostics feature; validate and allow-list any external input used for files, URLs or commands.
  4. Add anti-CSRF tokens, re-authentication for sensitive actions, and send framing / cookie-hardening headers.
  5. Restore secure session cookies (HttpOnly, SameSite=Lax) and lock down the CORS policy to a trusted origin.

4.0 Technical Findings

Each finding shows the vulnerable code as tested, then the mitigation (secure code).

F-01

SQL Injection — Authentication Bypass

Critical · 9.8
Location
auth/login.php
Impact
Log in as any user, including the administrator, with no valid password.
Proof of concept
Username admin'# with any password. The # comments out the password check, so the query returns the admin row and the session is granted. (' OR '1'='1'# logs in as the first user.)
Vulnerable
$username = param($_POST, 'username');
$password = password_param($_POST, 'password');

// User input concatenated straight into SQL.
$sql = "SELECT id FROM users
        WHERE username = '$username'
          AND password = '$password'";
$found = db()->query($sql)->fetch();

if ($found) {              // a returned row = "logged in"
    $_SESSION['user_id'] = $found['id'];
    redirect('/dashboard/');
}
Mitigation
$username = param($_POST, 'username');
$password = password_param($_POST, 'password');

// Parameterised query: input is data, not SQL.
$stmt = db()->prepare(
    'SELECT id, password_hash FROM users WHERE username = ?');
$stmt->execute([$username]);
$user = $stmt->fetch();

// Verify the hash in code; never store/compare plaintext.
if ($user && password_verify($password, $user['password_hash'])) {
    session_regenerate_id(true);
    $_SESSION['user_id'] = $user['id'];
    redirect('/dashboard/');
}

Recommendation. Use prepared statements for every query and verify passwords with password_verify(). Remove the plaintext password column.

F-02

OS Command Injection

Critical · 9.1
Location
admin/diagnostics.php (Server Diagnostics / ping tool)
Impact
Execute arbitrary commands on the host with the web server's privileges.
Proof of concept
Host value 127.0.0.1 & whoami (Windows) or 127.0.0.1; whoami (Linux) runs whoami after the ping and returns the server account name.
Vulnerable
$host = param($_GET, 'host');
$flag = stripos(PHP_OS,'WIN')===0 ? '-n 2' : '-c 2';

// Host string dropped straight into a shell command.
$output = shell_exec("ping $flag $host 2>&1");
Mitigation
$host = param($_GET, 'host');

// 1) Validate against a strict shape.
if (!filter_var($host, FILTER_VALIDATE_IP)) {
    exit('Enter a valid IP address.');
}
// 2) Escape the argument (and avoid the shell entirely).
$flag = stripos(PHP_OS,'WIN')===0 ? '-n 2' : '-c 2';
$output = shell_exec('ping '.$flag.' '.escapeshellarg($host).' 2>&1');
// Best: proc_open(['ping','-c','2',$host], ...) — no shell at all.

Recommendation. Avoid shells for user input. Validate to an allow-list, escape every argument, and prefer proc_open() with an argument array.

F-03

Broken Authentication

High · 8.1
Location
auth/login.php, includes/auth.php
Impact
Unlimited password guessing (no lockout); session fixation (session ID not rotated on login); session cookie readable by JavaScript.
Proof of concept
Repeated wrong passwords are never throttled or locked. The PHPSESSID value is identical before and after login.
Vulnerable
// No attempt counter, no delay, no lockout.
$found = db()->query($sql)->fetch();
if ($found) {
    $_SESSION['user_id'] = $found['id'];   // no session_regenerate_id()
}

// includes/auth.php — cookie weakened
session_set_cookie_params([
    'httponly' => false,     // JS can read the cookie
    'samesite' => 'None',    // sent cross-site
    'secure'   => true,
]);
Mitigation
// Throttle by username + IP, then lock.
if (failed_attempts($username) >= 5) {
    sleep(2); exit('Too many attempts. Try again later.');
}
if ($user && password_verify($password, $user['password_hash'])) {
    session_regenerate_id(true);           // new ID on login
    $_SESSION['user_id'] = $user['id'];
}

// Harden the session cookie.
session_set_cookie_params([
    'httponly' => true,      // JS cannot read it
    'samesite' => 'Lax',     // not sent on cross-site requests
    'secure'   => true,
]);

Recommendation. Add rate-limiting/lockout, rotate the session ID on login, and restore HttpOnly + SameSite=Lax.

F-04

Cross-Site Request Forgery — Account Takeover

High · 8.8
Location
banking/profile.php (password change)
Impact
Any page a logged-in victim visits can silently change their password and take over the account.
Proof of concept
While logged in, loading /banking/profile.php?action=password&new_password=hacked12345&confirm_password=hacked12345 (e.g. via attack-csrf.html) resets the password — no token, no current-password check.
Vulnerable
// Accepts GET or POST, no token, no re-auth.
$action = param($_POST,'action') ?: param($_GET,'action');
if ($action === 'password') {
    $new = password_param($_REQUEST, 'new_password');
    db()->prepare('UPDATE users SET password_hash=? WHERE id=?')
        ->execute([password_hash($new,PASSWORD_DEFAULT), $user['id']]);
}
Mitigation
if ($_SERVER['REQUEST_METHOD']==='POST'
    && param($_POST,'action')==='password') {

    // 1) Anti-CSRF token tied to the session.
    if (!hash_equals($_SESSION['csrf'] ?? '', $_POST['csrf'] ?? '')) {
        http_response_code(403); exit('Invalid request.');
    }
    // 2) Re-authenticate with the current password.
    if (!password_verify($current, $hash)) { /* reject */ }

    $new = password_param($_POST, 'new_password');
    db()->prepare('UPDATE users SET password_hash=? WHERE id=?')
        ->execute([password_hash($new,PASSWORD_DEFAULT), $user['id']]);
}

Recommendation. Require POST, a per-session CSRF token (hash_equals), and re-authentication for sensitive changes. SameSite=Lax cookies add defence in depth.

F-05

Server-Side Request Forgery

High · 8.6
Location
banking/profile.php ("profile picture from URL")
Impact
The server fetches any URL, reaching internal services and local files the attacker's browser cannot.
Proof of concept
file:///C:/Windows/win.ini returns a local file; file:///…/config/config.php leaks DB credentials; http://169.254.169.254/… targets cloud metadata.
Vulnerable
$url = param($_POST, 'avatar_url');

// Fetches whatever URL is given — any scheme, any host.
$body = file_get_contents($url);
Mitigation
$url = param($_POST, 'avatar_url');
$u   = parse_url($url);

// 1) Allow-list the scheme.
if (($u['scheme'] ?? '') !== 'https') exit('Only https URLs.');

// 2) Resolve host and block private / loopback / link-local IPs.
$ip = gethostbyname($u['host'] ?? '');
if (!filter_var($ip, FILTER_VALIDATE_IP,
        FILTER_FLAG_NO_PRIV_RANGE | FILTER_FLAG_NO_RES_RANGE)) {
    exit('Blocked internal address.');
}
// 3) Disable redirects so a public URL can't bounce inward.
$ctx  = stream_context_create(['http'=>['follow_location'=>0,'timeout'=>4]]);
$body = file_get_contents($url, false, $ctx);

Recommendation. Allow-list scheme and host, block private IP ranges after DNS resolution, disable redirects, and add an egress firewall.

F-06

Stored XSS — Cross-User

High · 8.0
Location
includes/txn-list.php (transaction description)
Impact
A transfer note written by the sender runs as script in the recipient's authenticated session.
Proof of concept
Arjun transfers to Priya with note <script>alert(document.cookie)</script>. When Priya opens her transactions, the script executes in her browser.
Vulnerable
<!-- description printed raw -->
<td class="txn-desc"><?= $t['description'] ?></td>
Mitigation
<!-- escape on output (htmlspecialchars) -->
<td class="txn-desc"><?= e($t['description']) ?></td>

Recommendation. Escape every user-controlled value on output with the e() helper (htmlspecialchars) and add a Content-Security-Policy.

F-07

Directory Traversal

High · 7.5
Location
banking/statements.php (?file= download)
Impact
Read arbitrary files outside the statements folder, including application source and secrets.
Proof of concept
?file=../../config/config.php returns the database credentials.
Vulnerable
$file = param($_GET, 'file');

// Filename joined to a path with no sanitisation.
$path = __DIR__ . '/statements/' . $file;
if (is_file($path)) readfile($path);
Mitigation
$file = param($_GET, 'file');

$dir  = realpath(__DIR__ . '/statements');
$path = realpath($dir . '/' . basename($file));   // basename drops ../

// Confirm the resolved path stays inside the folder.
if ($path === false ||
    !str_starts_with($path, $dir . DIRECTORY_SEPARATOR)) {
    http_response_code(404); exit('Not found');
}
readfile($path);

Recommendation. Strip the path with basename(), resolve with realpath(), and confirm it stays within the intended directory — or use an allow-list of filenames.

F-08

Clickjacking — One-Click Transfer

Medium · 6.5
Location
All responses (no framing headers); banking/transfer.php pre-fills from the URL.
Impact
A malicious site frames the pre-filled transfer page invisibly; a disguised click sends money to the attacker.
Proof of concept
attack-clickjack.html overlays a "leaderboard" button on an invisible, pre-filled transfer frame; clicking it submits the transfer.
Vulnerable
// No framing protection is sent anywhere, so any
// site may load the bank inside an <iframe>.
// (No X-Frame-Options / CSP frame-ancestors header.)
Mitigation
// Send on every response (includes/header.php or server config):
header("Content-Security-Policy: frame-ancestors 'none'");
header('X-Frame-Options: DENY');   // legacy fallback

// Also require a CSRF token + confirmation on transfer,
// and do not pre-fill the amount from the URL.

Recommendation. Send frame-ancestors 'none' (and X-Frame-Options: DENY), and protect state-changing actions with tokens and a confirmation step.

F-09

CORS Misconfiguration

Medium · 6.5
Location
api/balance.php
Impact
Any origin can read a logged-in customer's balances using their session cookie.
Proof of concept
A page on another origin runs fetch(url,{credentials:'include'}) and receives the account data (demonstrated from localhost:8095).
Vulnerable
// Reflects the caller's Origin AND allows credentials.
header('Access-Control-Allow-Origin: '.$_SERVER['HTTP_ORIGIN']);
header('Access-Control-Allow-Credentials: true');
Mitigation
$allowed = ['https://app.bankvwa.example'];
$origin  = $_SERVER['HTTP_ORIGIN'] ?? '';

// Only echo a trusted origin; never reflect arbitrary ones.
if (in_array($origin, $allowed, true)) {
    header("Access-Control-Allow-Origin: $origin");
    header('Access-Control-Allow-Credentials: true');
    header('Vary: Origin');
}

Recommendation. Keep a strict origin allow-list, never reflect Origin, and drop Allow-Credentials if cookies are not required.

F-10

Reflected XSS

Medium · 6.1
Location
banking/transactions.php (search term echo)
Impact
A crafted link runs attacker script in the victim's session (cookie theft, actions as the user).
Proof of concept
Searching <script>alert(document.cookie)</script> executes it in the results summary.
Vulnerable
<!-- search term echoed without escaping -->
... matching “<?= $q ?>”
Mitigation
<!-- escape on output -->
... matching “<?= e($q) ?>”

Recommendation. Escape reflected input with e() and deploy a Content-Security-Policy as a second layer.

5.0 Conclusion

BankVWA, as tested, is trivially compromised. The most likely attack path starts at the login page: a single SQL-injection string grants administrator access, after which the Server Diagnostics feature yields command execution on the host. Even without administrative access, a customer can read other customers' data (stored XSS, CORS), steal files (directory traversal, SSRF), and have money moved or passwords changed through a disguised click (clickjacking, CSRF).

The root causes are consistent and well understood: untrusted input is mixed into queries, commands, file paths, URLs and HTML output without validation or encoding, and standard protective headers and tokens are absent. Applying the mitigations above — parameterised queries, output encoding, allow-listed input, CSRF tokens, and security headers — would eliminate every finding in this report.
